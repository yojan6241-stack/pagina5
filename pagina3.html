G1.01El ciclo de vida de un proyecto

El ciclo de vida de un proyecto

El ciclo de vida de un proyecto informático describe las fases por las que atraviesa un desarrollo desde que se identifica una necesidad hasta que el sistema entra en producción y se mantiene. Habitualmente se distinguen las etapas de planificación, análisis, diseño, implementación, pruebas, despliegue y mantenimiento, cada una con entregables y criterios de salida propios. El modelo elegido -cascada, iterativo, incremental o ágil- condiciona cómo se transita entre estas fases y cuánta retroalimentación existe entre ellas. Documentar cada etapa permite trazar decisiones, controlar riesgos y planificar recursos con mayor precisión.

Un equipo divide el desarrollo de un sistema de facturación en sprints quincenales, revisando al final de cada uno los entregables frente a los requisitos iniciales.

El modelo en cascada, uno de los primeros formalizados para el ciclo de vida del software, fue descrito por Winston Royce en 1970.

G1.02Conceptos de análisis de aplicaciones

Conceptos de análisis de aplicaciones

El análisis de aplicaciones es la fase en la que se identifican y documentan las necesidades del negocio y de los usuarios antes de diseñar una solución técnica. Su objetivo es responder qué debe hacer el sistema, no cómo lo hará, delimitando el alcance funcional y no funcional del proyecto. Incluye técnicas como entrevistas, casos de uso, diagramas de flujo de datos e historias de usuario, que sirven para reducir la ambigüedad de los requisitos. Un análisis deficiente suele traducirse en retrabajo costoso en etapas posteriores del proyecto.

Un analista levanta los requisitos de un sistema de inventario entrevistando al personal de bodega antes de redactar la especificación funcional.

Los errores originados en la fase de análisis son, según numerosos estudios de ingeniería de software, los más costosos de corregir cuanto más tarde se detectan.

G1.03Conceptos de diseño de aplicaciones

Conceptos de diseño de aplicaciones

El diseño de aplicaciones traduce los requisitos obtenidos en el análisis a una arquitectura técnica concreta: estructura de módulos, modelo de datos, interfaces y flujos de interacción. Se distingue habitualmente entre diseño de alto nivel, que define la arquitectura general del sistema, y diseño detallado, que especifica algoritmos, estructuras de datos y componentes concretos. Un buen diseño busca cualidades como la modularidad, la cohesión interna de cada componente y el bajo acoplamiento entre ellos. Las decisiones tomadas aquí condicionan directamente la mantenibilidad futura del sistema.

Un equipo diseña la arquitectura de una aplicación en capas, separando la lógica de negocio del acceso a datos y de la interfaz de usuario.

El principio de bajo acoplamiento y alta cohesión, hoy estándar en el diseño de software, se popularizó a partir de los trabajos de Larry Constantine en los años setenta.

G1.04Conceptos generales del control de calidad

Conceptos generales del control de calidad

El control de calidad en el desarrollo de software es el conjunto de actividades planificadas para verificar que un producto cumple los requisitos definidos y los estándares acordados. Se apoya en dos enfoques complementarios: el aseguramiento de la calidad, orientado a prevenir defectos mediante procesos, y el control de calidad propiamente dicho, orientado a detectarlos mediante revisiones y pruebas. Entre sus técnicas habituales están las revisiones de código, las pruebas unitarias, de integración y de aceptación, y las métricas de defectos. Aplicar control de calidad de forma continua, y no solo al final del proyecto, reduce significativamente el costo de corrección.

Antes de liberar una nueva versión, el equipo ejecuta un conjunto de pruebas automatizadas y revisa manualmente los casos de uso críticos.

La norma ISO/IEC 25010, ampliamente usada como referencia de calidad de software, define ocho características principales como fiabilidad, usabilidad y mantenibilidad.

G1.05Control de calidad de las especificaciones funcionales

Control de calidad de las especificaciones funcionales

Las especificaciones funcionales describen con precisión qué debe hacer un sistema desde la perspectiva del usuario, y su control de calidad busca verificar que sean completas, consistentes, verificables y libres de ambigüedad. Una especificación deficiente -contradictoria, incompleta o redactada de forma vaga- se traslada como defecto a todas las fases posteriores del desarrollo. Las técnicas de revisión incluyen lecturas cruzadas entre analistas, listas de verificación y la trazabilidad de cada requisito hacia un caso de prueba concreto. Validar las especificaciones con los propios usuarios antes de iniciar el diseño reduce el riesgo de construir un sistema que no resuelve el problema real.

Un revisor detecta que dos requisitos del documento funcional se contradicen respecto al comportamiento esperado al eliminar un registro, y lo devuelve para aclaración.

La técnica de revisión por pares de especificaciones, formalizada por Michael Fagan en IBM durante los años setenta, sigue siendo la base de muchas inspecciones de calidad actuales.

G2.01Seguimiento de los requisitos de usuario

Seguimiento de los requisitos de usuario

El seguimiento de requisitos es el proceso de registrar, priorizar y controlar la evolución de las necesidades expresadas por los usuarios a lo largo del proyecto. Permite saber en todo momento qué requisitos están implementados, cuáles están pendientes y cuáles han cambiado respecto a la versión original. Herramientas como matrices de trazabilidad vinculan cada requisito con los diseños, el código y las pruebas que lo satisfacen. Sin un seguimiento adecuado, los cambios solicitados por los usuarios tienden a perderse o a implementarse de forma incompleta.

Un equipo mantiene una matriz de trazabilidad donde cada requisito de usuario queda vinculado a la funcionalidad, el módulo de código y el caso de prueba correspondiente.

La gestión formal de requisitos como disciplina propia de la ingeniería de software se consolidó especialmente durante los años noventa, con la aparición de herramientas dedicadas de trazabilidad.

G2.02Introducción a las bases de datos

Introducción a las bases de datos

Una base de datos es un conjunto organizado de datos relacionados entre sí, almacenados de forma estructurada para facilitar su acceso, gestión y actualización. Se gestiona mediante un sistema gestor de bases de datos (SGBD), un software que controla el almacenamiento físico, la seguridad, la concurrencia y la recuperación ante fallos. A diferencia de un simple archivo de datos, una base de datos está pensada para ser compartida por múltiples usuarios y aplicaciones sin perder consistencia. Su diseño adecuado es la base sobre la que se construye cualquier sistema de información moderno.

Una empresa centraliza en una única base de datos la información de clientes, pedidos y productos, en lugar de mantenerla dispersa en hojas de cálculo independientes.

El término 'base de datos' comenzó a popularizarse en los años sesenta, en paralelo al desarrollo de los primeros sistemas gestores comerciales.

G2.03Evolución histórica de las bases de datos

Evolución histórica de las bases de datos

Las bases de datos han evolucionado desde los sistemas de archivos planos de los años sesenta, pasando por los modelos jerárquico y de red, hasta la aparición del modelo relacional propuesto por Edgar Codd en 1970. El modelo relacional se impuso comercialmente en las décadas de los ochenta y noventa gracias a su solidez matemática y a la estandarización del lenguaje SQL. Más recientemente han surgido los sistemas NoSQL y NewSQL, orientados a escenarios de gran volumen, alta distribución o datos poco estructurados. Esta evolución responde a necesidades cambiantes de escalabilidad, flexibilidad y tipos de datos a gestionar.

Un sistema bancario de los años setenta basado en un modelo jerárquico migra décadas después a un motor relacional para ganar flexibilidad en sus consultas.

Edgar F. Codd publicó su artículo seminal sobre el modelo relacional, 'A Relational Model of Data for Large Shared Data Banks', en 1970 mientras trabajaba en IBM.

G2.04Ventajas e inconvenientes de las bases de datos

Ventajas e inconvenientes de las bases de datos

Frente al almacenamiento en archivos independientes, las bases de datos ofrecen ventajas como la reducción de la redundancia, el mantenimiento de la integridad de los datos, el acceso concurrente controlado y la independencia entre los datos y los programas que los usan. Como contrapartida, exigen una mayor complejidad de instalación y administración, un costo asociado al software gestor y al personal especializado, y una cuidadosa planificación de la seguridad y de las copias de respaldo. La decisión de adoptar un sistema de bases de datos suele justificarse quando el volumen de información o el número de usuarios concurrentes crece más allá de lo que un archivo simple puede sostener con fiabilidad. Evaluar estas ventajas e inconvenientes en cada proyecto evita adoptar una solución sobredimensionada o insuficiente.

Una pequeña tienda que antes registraba ventas en hojas de cálculo adopta una base de datos al notar inconsistencias entre los archivos usados por distintos empleados.

Los primeros sistemas gestores de bases de datos comerciales de los años setenta requerían equipos especializados de administradores dedicados exclusivamente a su operación.

G2.05Fundamentos del modelo relacional

Fundamentos del modelo relacional

El modelo relacional organiza los datos en tablas bidimensionales, llamadas relaciones, compuestas por filas (tuplas) y columnas (atributos), y se apoya en la teoría matemática de conjuntos y en la lógica de predicados. Su fortaleza radica en representar tanto los datos como las asociaciones entre ellos usando la misma estructura tabular, sin necesidad de punteros físicos explícitos. Sobre este modelo se definen operaciones formales de álgebra relacional -selección, proyección, unión, producto cartesiano- que sustentan lenguajes de consulta como SQL. Comprender estos fundamentos es indispensable antes de abordar el diseño, la normalización o la consulta de cualquier base de datos relacional.

Una tabla de 'Clientes' con columnas para nombre, dirección y correo electrónico ejemplifica una relación del modelo relacional, donde cada fila es un cliente distinto.

El álgebra relacional, base teórica del modelo, fue formalizada por Codd apoyándose en conceptos tomados directamente de la teoría de conjuntos matemática.

GRUPO3

Modelo relacional

G3.01Estructura del modelo relacional

Estructura del modelo relacional

La estructura del modelo relacional se compone de relaciones (tablas), atributos (columnas) y tuplas (filas), organizadas de forma que cada tabla representa un conjunto homogéneo de entidades o asociaciones. Cada atributo toma valores de un dominio definido, y el orden de las filas y columnas no tiene significado formal dentro del modelo. Esta estructura tabular, simple en apariencia, permite representar relaciones complejas entre distintos conjuntos de datos mediante claves que vinculan unas tablas con otras. Su uniformidad es precisamente lo que facilita la aplicación de operaciones de consulta estandarizadas sobre cualquier base de datos relacional.

Una tabla 'Empleados' y una tabla 'Departamentos' se vinculan mediante una columna común que representa la estructura relacional entre ambas entidades.

A diferencia del modelo jerárquico que lo precedió, el modelo relacional no exige rutas de acceso predefinidas para llegar a un dato.

G3.02El concepto de relación

El concepto de relación

En el modelo relacional, una relación es un subconjunto del producto cartesiano de varios dominios, y se representa visualmente como una tabla donde cada fila es una tupla y cada columna un atributo. El nombre 'relación' proviene precisamente de esta base matemática, y no debe confundirse coloquialmente con una 'asociación' entre tablas, aunque en la práctica ambos usos conviven. Formalmente, una relación tiene un esquema (el nombre de la tabla y sus atributos) y una instancia (el conjunto de tuplas presentes en un momento dado). Esta distinción entre esquema e instancia es clave para entender por qué el diseño de una base de datos puede evaluarse independientemente de los datos concretos que contenga.

El esquema Cliente(id, nombre, correo) define una relación; los registros concretos almacenados en un momento dado son su instancia.

El uso del término 'relación' con este sentido matemático, y no como sinónimo de vínculo entre tablas, procede directamente de la terminología introducida por Codd.

G3.03Propiedades de las relaciones

Propiedades de las relaciones

Las relaciones del modelo relacional cumplen propiedades formales: no existen tuplas duplicadas, el orden de las filas es irrelevante, el orden de las columnas es irrelevante y cada atributo contiene valores atómicos, es decir, no divisibles dentro del modelo. Estas propiedades derivan de que una relación es, matemáticamente, un conjunto, y los conjuntos no admiten elementos repetidos ni un orden intrínseco. En la práctica, los sistemas gestores suelen relajar alguna de estas propiedades por razones de rendimiento, por ejemplo permitiendo temporalmente filas duplicadas en resultados de consulta. Conocer estas propiedades ayuda a distinguir un diseño relacional correcto de uno que solo se parece superficialmente a una tabla.

Una tabla que no tiene una clave definida y permite dos filas idénticas se aparta, en sentido estricto, de la definición formal de relación.

La exigencia de valores atómicos por atributo es uno de los pilares que después dará origen a la primera forma normal dentro de la teoría de normalización.

G3.04Atributos y dominio de los atributos

Atributos y dominio de los atributos

Un atributo es cada una de las columnas que componen una relación, y representa una propiedad de la entidad o asociación que la tabla modela, como el nombre o la fecha de nacimiento de un cliente. El dominio de un atributo es el conjunto de valores válidos que puede tomar, ya sea un rango numérico, una lista de valores permitidos o un tipo de dato como texto o fecha. Definir dominios adecuados en el diseño de una base de datos es una forma temprana de garantizar la calidad de los datos, evitando que se almacenen valores incoherentes. Los sistemas gestores modernos permiten declarar dominios mediante tipos de datos, restricciones CHECK y tipos definidos por el usuario.

El atributo 'edad' de una tabla de empleados se restringe a un dominio de números enteros positivos razonables, evitando valores como -5 o 300.

El concepto de dominio en el modelo relacional antecede y fundamenta el uso posterior de los tipos de datos tal como se conocen en SQL.

G3.05Claves: candidatas, primarias, alternativas y ajenas

Claves: candidatas, primarias, alternativas y ajenas

Una clave candidata es cualquier conjunto mínimo de atributos que identifica de forma única cada tupla de una relación; entre todas las claves candidatas se elige una como clave primaria, y el resto se denominan claves alternativas. La clave ajena, o foránea, es un atributo o conjunto de atributos de una tabla que hace referencia a la clave primaria de otra tabla, y es el mecanismo principal para representar relaciones entre entidades. El uso correcto de claves garantiza tanto la identificación única de los registros como la integridad referencial entre tablas relacionadas. Elegir mal una clave primaria -por ejemplo usando un dato que puede cambiar, como un correo electrónico- suele generar problemas de mantenimiento a futuro.

En una tabla 'Pedidos', el atributo 'id_cliente' es una clave ajena que referencia la clave primaria de la tabla 'Clientes'.

El uso de identificadores numéricos autogenerados como clave primaria, en lugar de datos naturales como el DNI o el correo, es una práctica extendida precisamente para evitar dependencias de datos que pueden cambiar.

Integridad y modelo entidad-relación

G4.01Restricciones de integridad

Restricciones de integridad

Las restricciones de integridad son reglas que garantizan la consistencia y corrección de los datos almacenados en una base de datos a lo largo del tiempo. Se clasifican principalmente en integridad de entidad, que exige que la clave primaria no admita valores nulos ni duplicados, e integridad referencial, que exige que toda clave ajena coincida con un valor existente en la tabla referenciada o sea nula. A estas se suman restricciones definidas por el usuario, como rangos de valores permitidos o reglas de negocio específicas. Aplicar estas restricciones a nivel del propio motor de base de datos, y no solo en la aplicación, evita que datos inconsistentes lleguen a almacenarse por error o por accesos concurrentes no previstos.

Un sistema impide eliminar un cliente que todavía tiene pedidos asociados, por respetar una restricción de integridad referencial.

La integridad referencial, aunque hoy se da por hecha en cualquier motor relacional, no se implementó de forma generalizada y eficiente en los sistemas comerciales hasta bien entrados los años ochenta.

G4.02El modelo entidad-relación

El modelo entidad-relación

El modelo entidad-relación (E-R) es una herramienta conceptual para diseñar bases de datos representando el mundo real como un conjunto de entidades, sus atributos y las relaciones que existen entre ellas, antes de traducirlo a un esquema relacional concreto. Propuesto por Peter Chen en 1976, se usa en la fase de diseño conceptual, independientemente del sistema gestor que finalmente implemente la base de datos. Su principal ventaja es servir como lenguaje común entre analistas, diseñadores y usuarios de negocio, ya que su notación gráfica es más intuitiva que un esquema de tablas. A partir del modelo E-R se deriva, mediante reglas de transformación bien definidas, el esquema relacional final.

Antes de crear las tablas de una tienda en línea, el equipo dibuja un diagrama entidad-relación con las entidades Cliente, Pedido y Producto y sus vínculos.

Peter Chen presentó el modelo entidad-relación en un artículo de 1976 que se convirtió en una de las referencias más citadas de la ingeniería de bases de datos.

G4.03Entidades, relaciones y atributos

Entidades, relaciones y atributos

En el modelo entidad-relación, una entidad representa un objeto o concepto del mundo real sobre el que se desea almacenar información, como un cliente o un producto; una relación representa una asociación significativa entre dos o más entidades, como 'compra' entre cliente y producto; y un atributo describe una propiedad de una entidad o de una relación, como el nombre de un cliente o la fecha de una compra. Las relaciones pueden clasificarse según su cardinalidad -uno a uno, uno a muchos o muchos a muchos- lo que determina cómo se traducirán posteriormente a tablas y claves ajenas. Distinguir correctamente qué es una entidad y qué es una relación en la fase de diseño conceptual evita ambigüedades que después se arrastran al esquema físico.

La relación 'Matricula' entre las entidades 'Estudiante' y 'Curso' puede tener su propio atributo, como la fecha de matriculación.

Las relaciones muchos a muchos del modelo entidad-relación se traducen siempre, al pasar al modelo relacional, en una tabla intermedia propia.

G4.04Diagramas entidad-relación

Diagramas entidad-relación

Un diagrama entidad-relación representa gráficamente las entidades, atributos y relaciones de un dominio mediante una notación estandarizada, típicamente rectángulos para entidades, óvalos para atributos y rombos para relaciones, aunque existen variantes como la notación de Chen o la notación de pie de gallina (crow's foot). Estos diagramas permiten visualizar de un vistazo la cardinalidad y opcionalidad de cada relación, información clave para el diseño posterior de las tablas y sus claves. Son además una herramienta de comunicación y validación con los usuarios de negocio, que pueden revisar el diagrama sin necesidad de conocer SQL. Un diagrama E-R bien construido reduce significativamente los errores de diseño detectados en etapas posteriores del proyecto.

Un diagrama E-R muestra que un 'Departamento' puede tener muchos 'Empleados', pero cada 'Empleado' pertenece a un único 'Departamento'.

La notación de pie de gallina, muy usada hoy en herramientas de modelado, debe su nombre a la forma que adoptan las líneas que indican cardinalidad múltiple.

G4.05Teoría de normalización

Teoría de normalización

La teoría de normalización es un conjunto de reglas formales que guían el diseño de tablas relacionales para reducir la redundancia de datos y evitar anomalías de inserción, actualización y borrado. Se organiza en una serie de formas normales -primera, segunda, tercera, Boyce-Codd, y otras más avanzadas- cada una más estricta que la anterior en cuanto a las dependencias que permite entre atributos. Un esquema normalizado divide la información en tablas más pequeñas y especializadas, relacionadas entre sí mediante claves, en lugar de concentrarla en tablas amplias con datos repetidos. Aunque la normalización mejora la integridad de los datos, en ciertos escenarios de alto rendimiento se aplica una desnormalización deliberada y controlada.

Una tabla que repite el nombre de la ciudad en cada pedido de un cliente se normaliza separando esa información en una tabla independiente de clientes.

La teoría de normalización fue desarrollada por Edgar Codd como una extensión directa y natural de su propio modelo relacional.

GRUPO5

Normalización y lenguaje DDL

G5.01El proceso de normalización

El proceso de normalización

El proceso de normalización consiste en aplicar sucesivamente las formas normales a un esquema de base de datos, verificando en cada paso qué dependencias funcionales existen entre los atributos y descomponiendo las tablas cuando sea necesario para eliminarlas. Se parte habitualmente de un esquema no normalizado o de un modelo entidad-relación recién traducido a tablas, y se avanza forma por forma hasta alcanzar el nivel de normalización que el proyecto requiera, comúnmente la tercera forma normal. Cada descomposición debe preservar tanto la información original como las dependencias funcionales existentes, para no perder capacidad de consulta ni introducir inconsistencias nuevas. El resultado es un conjunto de tablas más pequeñas, con menor redundancia y menos susceptibles a anomalías al insertar, actualizar o eliminar datos.

Al normalizar una tabla de pedidos que incluye los datos completos del producto en cada línea, el equipo separa esa información en una tabla de productos independiente.

El proceso de normalización se describe habitualmente como una serie de pasos incrementales, y rara vez se aplica una única forma normal de forma aislada.

G5.02Tipos de dependencias funcionales

Tipos de dependencias funcionales

Una dependencia funcional expresa que el valor de un atributo (o conjunto de atributos) determina de forma única el valor de otro atributo dentro de una relación. Se distinguen dependencias funcionales completas, cuando un atributo depende de toda la clave y no de una parte de ella, y dependencias funcionales parciales, cuando depende solo de parte de una clave compuesta. También son relevantes las dependencias transitivas, en las que un atributo depende de otro que a su vez depende de la clave, y no directamente de esta. Identificar correctamente estos tipos de dependencias es el paso previo indispensable para aplicar la segunda y la tercera forma normal.

En una tabla con clave compuesta (id_pedido, id_producto), el atributo 'nombre_cliente' depende solo de id_pedido, lo que evidencia una dependencia funcional parcial.

El concepto de dependencia funcional, central en toda la teoría de normalización, fue formalizado matemáticamente por Codd como parte de su trabajo original sobre el modelo relacional.

G5.03Lenguaje de definición de datos (DDL)

Lenguaje de definición de datos (DDL)

El lenguaje de definición de datos (DDL, por sus siglas en inglés) es el subconjunto de SQL utilizado para crear, modificar y eliminar la estructura de los objetos de una base de datos, como tablas, índices y vistas. Sus sentencias principales son CREATE, ALTER y DROP, que actúan sobre el esquema de la base de datos y no directamente sobre los datos almacenados en ella. A diferencia del lenguaje de manipulación de datos, las operaciones DDL suelen confirmarse de forma automática (commit implícito) en la mayoría de los motores relacionales. Dominar el DDL es indispensable para poder traducir un diseño relacional, ya normalizado, en una base de datos física funcional.

Un administrador utiliza una sentencia CREATE TABLE para definir la estructura de la tabla 'Clientes' con sus columnas y restricciones.

El estándar SQL, que formaliza el DDL entre otros componentes, fue adoptado por ANSI por primera vez en 1986 y luego por ISO en 1987.

G5.04Creación y borrado de bases de datos

Creación y borrado de bases de datos

La creación de una base de datos mediante DDL se realiza típicamente con la sentencia CREATE DATABASE, que reserva el espacio y establece la configuración inicial -como el conjunto de caracteres o el motor de almacenamiento- donde después se alojarán las tablas y demás objetos. El borrado, mediante DROP DATABASE, elimina de forma permanente e irreversible tanto la estructura como todos los datos contenidos en ella, por lo que suele restringirse a usuarios con privilegios administrativos. Antes de ejecutar un borrado de este tipo en un entorno de producción es práctica habitual verificar que existan copias de respaldo recientes. Estas operaciones marcan el punto de partida y de cierre del ciclo de vida físico de una base de datos.

Un administrador ejecuta CREATE DATABASE tienda_online antes de comenzar a crear las tablas que compondrán el sistema.

En la mayoría de los motores relacionales, la sentencia DROP DATABASE no puede deshacerse una vez confirmada, salvo mediante la restauración de una copia de respaldo previa.

G5.05Creación y borrado de tablas

Creación y borrado de tablas

La creación de tablas mediante la sentencia CREATE TABLE define el nombre de la tabla, sus columnas, los tipos de datos de cada una y las restricciones asociadas, como claves primarias, claves ajenas o valores por defecto. El borrado de una tabla, mediante DROP TABLE, elimina tanto su estructura como todos los datos que contenía, mientras que la sentencia TRUNCATE TABLE, relacionada pero distinta, vacía los datos conservando la estructura. Antes de eliminar una tabla, el motor suele verificar que no existan restricciones de integridad referencial que dependan de ella, para evitar dejar la base de datos en un estado inconsistente. Diseñar correctamente esta fase es la materialización directa del esquema relacional obtenido tras el proceso de normalización.

CREATE TABLE Clientes (id INT PRIMARY KEY, nombre VARCHAR(100), correo VARCHAR(150)); define una tabla básica de clientes.

A diferencia de DROP TABLE, la sentencia TRUNCATE suele ejecutarse de forma más rápida porque, en muchos motores, no registra la eliminación fila por fila.

Objetos de la base de datos

G6.01Creación y borrado de índices

Creación y borrado de índices

Un índice es un objeto de la base de datos que acelera la búsqueda y recuperación de registros, a costa de espacio de almacenamiento adicional y de un ligero costo extra en las operaciones de escritura. Se crea mediante la sentencia CREATE INDEX sobre una o varias columnas de una tabla, y se elimina con DROP INDEX cuando deja de ser útil o penaliza más de lo que beneficia. Los motores relacionales suelen implementar los índices internamente mediante estructuras como árboles B+ o tablas hash, que permiten localizar un registro sin recorrer la tabla completa. Elegir qué columnas indexar es una decisión de rendimiento que debe basarse en los patrones reales de consulta del sistema, no aplicarse de forma indiscriminada.

CREATE INDEX idx_correo ON Clientes(correo); acelera las búsquedas de clientes por dirección de correo electrónico.

Un índice mal elegido puede llegar a ralentizar un sistema en lugar de acelerarlo, al añadir sobrecarga en cada operación de inserción o actualización sin aportar beneficio real a las consultas.

Lenguaje DML

G7.01Lenguaje de manipulación de datos (DML)

Lenguaje de manipulación de datos (DML)

El lenguaje de manipulación de datos (DML) es el subconjunto de SQL utilizado para consultar y modificar el contenido de las tablas, una vez que su estructura ya ha sido definida mediante DDL. Sus sentencias principales son SELECT, INSERT, UPDATE y DELETE, que permiten respectivamente consultar, insertar, modificar y eliminar registros. A diferencia del DDL, las operaciones DML suelen formar parte de transacciones que pueden confirmarse (COMMIT) o deshacerse (ROLLBACK) explícitamente. El DML es, en la práctica diaria, el lenguaje más utilizado por las aplicaciones para interactuar con la base de datos.

Una aplicación de ventas ejecuta una sentencia INSERT cada vez que se registra un nuevo pedido en el sistema.

El DML es el componente de SQL con el que interactúan con mayor frecuencia tanto los desarrolladores de aplicaciones como los analistas de datos.

G7.02Construcción de consultas de selección

Construcción de consultas de selección

Las consultas de selección, construidas con la sentencia SELECT, permiten recuperar datos de una o varias tablas especificando qué columnas se desean obtener y, opcionalmente, qué condiciones deben cumplir las filas mediante la cláusula WHERE. Pueden combinarse con JOIN para relacionar varias tablas, con ORDER BY para ordenar los resultados y con alias para mejorar la legibilidad de la consulta. La correcta construcción de una consulta de selección depende de entender tanto el esquema de las tablas involucradas como las claves que las relacionan. Es, con diferencia, la operación SQL que con más frecuencia ejecutan tanto las aplicaciones como los propios usuarios de negocio.

SELECT nombre, correo FROM Clientes WHERE ciudad = 'Guatemala'; recupera el nombre y correo de los clientes de una ciudad específica.

La cláusula SELECT * , aunque cómoda para explorar datos rápidamente, suele evitarse en aplicaciones de producción por motivos de rendimiento y de mantenibilidad.

G7.03Construcción de consultas de inserción

Construcción de consultas de inserción

Las consultas de inserción, construidas con la sentencia INSERT INTO, agregan nuevas filas a una tabla especificando los valores para cada columna, ya sea de forma explícita o seleccionando datos provenientes de otra consulta. El motor de base de datos verifica automáticamente que los valores insertados respeten las restricciones de integridad definidas, como claves primarias no repetidas o claves ajenas válidas. Es posible insertar una única fila o múltiples filas en una sola sentencia, lo que resulta más eficiente que ejecutar inserciones individuales repetidas. Una inserción rechazada por violar una restricción es, en la práctica, una de las primeras señales de un problema de calidad en los datos de origen.

INSERT INTO Clientes (nombre, correo) VALUES ('Ana López', 'ana@correo.com'); agrega un nuevo cliente a la tabla.

Insertar múltiples filas en una sola sentencia INSERT suele ser considerablemente más eficiente que ejecutar una sentencia independiente por cada fila.

G7.04Construcción de consultas de modificación

Construcción de consultas de modificación

Las consultas de modificación, construidas con la sentencia UPDATE, actualizan los valores de una o varias columnas en las filas que cumplen una condición determinada por la cláusula WHERE. Omitir la cláusula WHERE por error es uno de los fallos más comunes y peligrosos al trabajar con UPDATE, ya que provoca que la modificación se aplique a todas las filas de la tabla. Es posible actualizar varias columnas en una misma sentencia, e incluso basar los nuevos valores en los datos de otras tablas mediante subconsultas o combinaciones. Antes de ejecutar una actualización masiva en un entorno de producción, es una buena práctica probar primero la condición equivalente con una sentencia SELECT.

UPDATE Clientes SET ciudad = 'Antigua Guatemala' WHERE id = 15; actualiza la ciudad de un cliente específico identificado por su clave primaria.

Ejecutar un UPDATE sin cláusula WHERE es uno de los errores más citados en la administración de bases de datos por el alcance inesperado que provoca.

G7.05Construcción de consultas de borrado

Construcción de consultas de borrado

Las consultas de borrado, construidas con la sentencia DELETE, eliminan filas de una tabla según una condición especificada en la cláusula WHERE, sin afectar la estructura de la tabla en sí. Al igual que ocurre con UPDATE, omitir la condición WHERE provoca la eliminación de todas las filas de la tabla, por lo que suele recomendarse envolver estas operaciones en transacciones controladas. El motor de base de datos verifica también, antes de ejecutar el borrado, que no existan restricciones de integridad referencial que impidan eliminar una fila referenciada desde otra tabla. Distinguir DELETE de TRUNCATE es importante: el primero puede filtrarse y deshacerse dentro de una transacción, mientras que el segundo suele ser una operación más rápida pero menos flexible.

DELETE FROM Pedidos WHERE estado = 'cancelado'; elimina únicamente los pedidos marcados como cancelados.

A diferencia de TRUNCATE, la sentencia DELETE puede combinarse con una cláusula WHERE para eliminar solo un subconjunto específico de filas.

G8.01Agrupación y ordenación de consultas

Agrupación y ordenación de consultas

La agrupación de resultados mediante la cláusula GROUP BY reúne filas que comparten un mismo valor en una o varias columnas, permitiendo aplicar funciones agregadas sobre cada grupo por separado, como contar o sumar. La ordenación mediante ORDER BY, en cambio, no agrupa datos sino que organiza el resultado final de la consulta según uno o varios criterios, en orden ascendente o descendente. Ambas cláusulas suelen combinarse en una misma consulta, por ejemplo para mostrar el total de ventas por cliente ordenado de mayor a menor. Es importante recordar que toda columna que aparezca en el SELECT sin estar agregada debe formar parte del GROUP BY, una regla que el motor de base de datos exige para evitar resultados ambiguos.

SELECT ciudad, COUNT(*) FROM Clientes GROUP BY ciudad ORDER BY COUNT(*) DESC; muestra cuántos clientes hay por ciudad, de mayor a menor.

La cláusula GROUP BY se ejecuta lógicamente después del WHERE pero antes del ORDER BY, un orden que explica por qué ciertas condiciones deben ir en HAVING y no en WHERE.

G8.02Operaciones aritméticas, lógicas y de comparación

Operaciones aritméticas, lógicas y de comparación

SQL permite combinar operaciones aritméticas (+, -, *, /), operadores de comparación (=, <>, <, >, <=, >=) y operadores lógicos (AND, OR, NOT) directamente dentro de las cláusulas SELECT y WHERE, lo que posibilita construir condiciones y cálculos complejos en una misma consulta. El orden de evaluación de estos operadores sigue reglas de precedencia similares a las del álgebra tradicional, y el uso de paréntesis permite controlar explícitamente ese orden cuando existe ambigüedad. Los operadores lógicos son especialmente relevantes para combinar múltiples condiciones de filtrado dentro de una misma cláusula WHERE. Un uso descuidado de la precedencia entre AND y OR es una fuente frecuente de errores lógicos en consultas aparentemente correctas.

SELECT * FROM Productos WHERE precio > 100 AND (categoria = 'electronica' OR categoria = 'hogar'); combina comparación y lógica en una sola condición.

Olvidar los paréntesis al combinar AND y OR en una cláusula WHERE es una de las causas más comunes de resultados inesperados en consultas SQL.

G8.03Funciones agregadas

Funciones agregadas

Las funciones agregadas de SQL -COUNT, SUM, AVG, MAX y MIN, entre otras- operan sobre un conjunto de filas y devuelven un único valor resumen, como el total de registros, la suma de una columna numérica o el promedio de un conjunto de valores. Se utilizan habitualmente junto con GROUP BY para calcular resúmenes por categoría, aunque también pueden aplicarse sobre toda la tabla sin agrupar. La cláusula HAVING permite filtrar los resultados después de que la agregación se haya calculado, algo que WHERE no puede hacer porque actúa antes de agrupar. Estas funciones son la base de la mayoría de los reportes e indicadores construidos directamente sobre una base de datos relacional.

SELECT categoria, AVG(precio) FROM Productos GROUP BY categoria HAVING AVG(precio) > 50; muestra las categorías cuyo precio promedio supera un umbral.

La función COUNT(*) cuenta todas las filas de un grupo incluyendo aquellas con valores nulos, mientras que COUNT(columna) ignora los valores nulos de esa columna específica.

G8.04Tratamiento de valores nulos

Tratamiento de valores nulos

Un valor nulo (NULL) en SQL representa la ausencia de un dato o un valor desconocido, y se comporta de forma distinta a un valor vacío o a cero, lo que exige un tratamiento especial en las consultas. Las comparaciones tradicionales como igual (=) o distinto (<>) no funcionan con NULL, por lo que es necesario usar los operadores IS NULL e IS NOT NULL para evaluarlos correctamente. La mayoría de las funciones agregadas ignoran los valores nulos en sus cálculos, salvo COUNT(*), lo que puede generar resultados inesperados si no se comprende esta particularidad. Definir explícitamente qué columnas permiten valores nulos durante el diseño de la tabla es una decisión que impacta directamente en la calidad e integridad de los datos.

SELECT * FROM Clientes WHERE telefono IS NULL; identifica los clientes que no tienen registrado un número de teléfono.

En la lógica de tres valores que utiliza SQL para NULL, una comparación como NULL = NULL no devuelve verdadero, sino un resultado desconocido.

G8.05Construcción de consultas anidadas

Construcción de consultas anidadas

Una consulta anidada, o subconsulta, es una sentencia SELECT que se ejecuta dentro de otra consulta, ya sea en la cláusula WHERE, FROM o SELECT, y cuyo resultado se utiliza como parte de la consulta principal. Puede devolver un único valor, una lista de valores o incluso una tabla completa, dependiendo del contexto en que se utilice, y suele combinarse con operadores como IN, EXISTS o comparaciones directas. Las subconsultas permiten expresar condiciones que dependen de datos calculados dinámicamente, algo que sería difícil de lograr con una única consulta plana. Aunque muy expresivas, las subconsultas mal construidas pueden afectar el rendimiento, por lo que en ciertos casos se prefieren combinaciones (JOIN) equivalentes.

SELECT nombre FROM Clientes WHERE id IN (SELECT id_cliente FROM Pedidos WHERE total > 1000); identifica clientes con pedidos superiores a un monto.

En muchos motores relacionales, una subconsulta correlacionada -que hace referencia a la consulta externa- se ejecuta una vez por cada fila de esta, lo que puede impactar el rendimiento si no se optimiza.

G9.01Unión, intersección y diferencia de consultas

Unión, intersección y diferencia de consultas

Los operadores de conjuntos en SQL -UNION, INTERSECT y EXCEPT (o MINUS, según el motor)- combinan los resultados de dos o más consultas que devuelven el mismo número de columnas con tipos compatibles. UNION combina las filas de ambas consultas eliminando duplicados, mientras que UNION ALL las combina conservándolos; INTERSECT devuelve solo las filas presentes en ambos resultados; y EXCEPT devuelve las filas del primer resultado que no aparecen en el segundo. Estas operaciones provienen directamente del álgebra relacional y de la teoría de conjuntos sobre la que se construye el modelo relacional. Son especialmente útiles para comparar o combinar información proveniente de tablas estructuralmente similares pero con datos distintos.

SELECT ciudad FROM Clientes INTERSECT SELECT ciudad FROM Proveedores; devuelve solo las ciudades donde hay tanto clientes como proveedores.

UNION ALL suele ejecutarse más rápido que UNION porque, al no eliminar duplicados, el motor se ahorra el costo de comparar y filtrar filas repetidas.

G9.02Consultas de tablas cruzadas

Consultas de tablas cruzadas

Una consulta de tabla cruzada, o tabla dinámica (pivot), reorganiza los datos de un resultado convirtiendo los valores de una columna en nuevas columnas del resultado final, facilitando la lectura de resúmenes con dos dimensiones de análisis, como ventas por producto y por mes. Algunos motores relacionales ofrecen sentencias específicas como PIVOT, mientras que en otros se construye de forma manual combinando funciones agregadas con expresiones condicionales (CASE WHEN). Este tipo de consultas es especialmente valorado en informes gerenciales, donde se necesita comparar categorías de forma visual y compacta. Su construcción manual, aunque más laboriosa, ofrece mayor control sobre el resultado final que las herramientas de pivote automáticas.

Una consulta de tabla cruzada muestra el total de ventas de cada producto distribuido en columnas por trimestre del año.

La operación de pivote, aunque conceptualmente sencilla, no forma parte del estándar SQL original y su sintaxis varía notablemente entre distintos motores de bases de datos.

G9.03Extensiones del lenguaje

Extensiones del lenguaje

Además del núcleo estándar de SQL, la mayoría de los sistemas gestores incorporan extensiones propias del lenguaje: funciones específicas del motor, tipos de datos adicionales, sentencias procedimentales para crear procedimientos almacenados y funciones, o cláusulas de paginación de resultados. Estas extensiones facilitan tareas comunes que el estándar SQL no siempre resuelve de forma directa, pero a cambio reducen la portabilidad del código entre distintos motores. Conocer la diferencia entre SQL estándar y las extensiones propias de cada motor es importante al planificar una posible migración entre sistemas gestores. Ejemplos habituales de estas extensiones son PL/pgSQL en PostgreSQL o T-SQL en SQL Server.

Una consulta que usa LIMIT para paginar resultados en un motor y OFFSET FETCH en otro ilustra cómo cada sistema extiende el estándar SQL a su manera.

Aunque el estándar SQL busca la portabilidad entre motores, en la práctica cada sistema gestor añade extensiones propias que dificultan mover el código sin ajustes.

G9.04Creación, manipulación y borrado de vistas

Creación, manipulación y borrado de vistas

Una vista es una tabla virtual definida a partir de una consulta SQL almacenada, que no guarda físicamente los datos sino que los calcula cada vez que se consulta, mostrando siempre información actualizada de las tablas subyacentes. Se crea con CREATE VIEW, se puede modificar con CREATE OR REPLACE VIEW o ALTER VIEW según el motor, y se elimina con DROP VIEW sin afectar a las tablas originales. Las vistas simplifican consultas complejas repetitivas, ocultan la complejidad del esquema real a ciertos usuarios y pueden usarse también como mecanismo de seguridad, restringiendo el acceso a columnas o filas específicas. No todas las vistas admiten operaciones de inserción, actualización o borrado directamente sobre ellas, especialmente cuando combinan datos de varias tablas.

CREATE VIEW ClientesActivos AS SELECT * FROM Clientes WHERE activo = 1; simplifica el acceso repetido a un subconjunto frecuente de datos.

Una vista no almacena datos propios: cada vez que se consulta, el motor vuelve a ejecutar internamente la sentencia SELECT que la define.

G9.05Especificación de restricciones de integridad

Especificación de restricciones de integridad

Además de las claves primarias y ajenas, SQL permite especificar restricciones de integridad adicionales directamente en la definición de una tabla: NOT NULL para exigir un valor, UNIQUE para evitar duplicados, CHECK para validar una condición sobre los datos, y DEFAULT para asignar un valor automático cuando no se proporciona uno. Estas restricciones se declaran habitualmente dentro de la sentencia CREATE TABLE, aunque también pueden añadirse o modificarse posteriormente con ALTER TABLE. Aplicar estas reglas directamente en el motor de base de datos, en lugar de confiar únicamente en la validación de la aplicación, protege los datos frente a cualquier vía de acceso, incluidas conexiones directas o errores de programación. Una especificación de restricciones bien pensada reduce considerablemente la necesidad de código de validación repetido en distintas aplicaciones.

CREATE TABLE Productos (id INT PRIMARY KEY, precio DECIMAL(10,2) CHECK (precio > 0)); impide almacenar productos con precio negativo o cero.

Definir las restricciones de integridad a nivel de base de datos, y no solo en la aplicación, evita que datos inválidos entren al sistema por vías de acceso alternativas no previstas.

G10.01Instrucciones de autorización

Instrucciones de autorización

Las instrucciones de autorización en SQL -GRANT y REVOKE- controlan qué usuarios o roles pueden realizar determinadas operaciones sobre los objetos de una base de datos, como consultar, insertar, modificar o eliminar datos, o incluso administrar la propia estructura. GRANT concede un permiso específico a un usuario o rol, mientras que REVOKE lo retira, permitiendo ajustar de forma granular el nivel de acceso de cada persona o aplicación. Este mecanismo, parte del lenguaje de control de datos (DCL) dentro de SQL, es fundamental para aplicar el principio de mínimo privilegio, otorgando a cada usuario solo los permisos estrictamente necesarios para su función. Una gestión descuidada de estos privilegios es una de las causas más frecuentes de incidentes de seguridad en bases de datos.

GRANT SELECT, INSERT ON Pedidos TO aplicacion_ventas; concede permisos limitados a un usuario de aplicación sin darle acceso administrativo.

El principio de mínimo privilegio, aplicado mediante GRANT y REVOKE, sigue siendo una de las recomendaciones de seguridad más citadas en la administración de bases de datos.

G10.02Lenguaje de Marcado Extensible (XML)

Lenguaje de Marcado Extensible (XML)

XML (Extensible Markup Language) es un lenguaje de marcado diseñado para almacenar y transportar datos de forma estructurada y legible tanto por personas como por máquinas, usando etiquetas definidas por el propio usuario en lugar de un conjunto fijo predeterminado. A diferencia de HTML, que define cómo mostrar información, XML define cómo describir y estructurar datos, lo que lo hace especialmente útil para el intercambio de información entre sistemas distintos. Muchos motores de bases de datos relacionales incorporan un tipo de dato XML nativo y funciones específicas para almacenar, consultar y validar documentos XML dentro de la propia base de datos. Su estructura jerárquica y auto-descriptiva facilita la interoperabilidad entre aplicaciones que, de otro modo, no compartirían un formato común.

G10.03Creación de datos en ejecución de consultas

Creación de datos en ejecución de consultas

Algunos motores relacionales permiten generar y transformar datos directamente durante la ejecución de una consulta, mediante columnas calculadas, expresiones CASE WHEN, funciones de fecha o cadena, y la generación de valores derivados que no existen almacenados como tales en ninguna tabla. Esta capacidad evita tener que materializar físicamente cada dato posible, calculándolo únicamente en el momento en que se necesita para el resultado de una consulta específica. También incluye mecanismos como columnas generadas (computed columns) o secuencias, que producen valores automáticamente sin intervención directa del usuario. Aprovechar esta capacidad del lenguaje reduce la redundancia de datos almacenados y mantiene la consistencia, ya que el valor se calcula siempre a partir de la misma fuente.

SELECT nombre, CASE WHEN edad >= 18 THEN 'Adulto' ELSE 'Menor' END AS categoria FROM Personas; genera una columna nueva a partir de una condición durante la consulta.

Las columnas calculadas o generadas evitan almacenar un dato redundante que podría desincronizarse de la información original si se guardara de forma independiente.

G10.04Aplicación de comandos SQL

Aplicación de comandos SQL

La aplicación práctica de los comandos SQL combina, en una única solución, sentencias DDL para definir la estructura, DML para manipular los datos y DCL para controlar los accesos, todo ello dentro de un flujo de trabajo coherente que respeta las restricciones de integridad definidas. Comprender cómo interactúan estos comandos entre sí -por ejemplo, cómo una restricción definida en DDL condiciona lo que un INSERT en DML puede hacer- es lo que distingue el conocimiento aislado de sentencias sueltas del dominio real del lenguaje. En un entorno de trabajo típico, estos comandos se combinan también con transacciones, que agrupan varias sentencias para que se ejecuten como una unidad indivisible. La práctica constante con casos reales es lo que consolida la capacidad de traducir un requisito de negocio en la secuencia correcta de comandos SQL.

Un desarrollador crea una tabla con DDL, la puebla con datos de prueba usando DML y limita su acceso a un usuario concreto mediante DCL, todo dentro de un mismo script.

Agrupar sentencias DDL, DML y DCL dentro de una transacción, cuando el motor lo permite, garantiza que un conjunto de cambios se aplique de forma completa o no se aplique en absoluto.

G10.05Formato de archivos para exportación

Formato de archivos para exportación

Exportar datos desde una base de datos implica convertirlos a un formato de archivo adecuado para su uso fuera del sistema gestor, siendo los más comunes CSV para datos tabulares simples, JSON para estructuras jerárquicas y de fácil integración con aplicaciones web, y XML cuando se requiere una estructura auto-descriptiva y validable. La elección del formato depende del sistema destino, del volumen de datos y de si se necesita preservar tipos de datos complejos o relaciones jerárquicas entre la información. La mayoría de los motores relacionales incluyen herramientas o comandos específicos para exportar el resultado de una consulta directamente a estos formatos, sin necesidad de procesamiento adicional externo. Elegir un formato de exportación adecuado facilita la interoperabilidad entre sistemas que, de otro modo, no podrían intercambiar información entre sí.

Un sistema exporta el reporte mensual de ventas a un archivo CSV para que el equipo administrativo lo abra directamente en una hoja de cálculo.

El formato CSV, pese a su simplicidad, sigue siendo uno de los formatos de exportación más utilizados por su compatibilidad casi universal con herramientas de análisis de datos.

G11.01Entornos de desarrollo de gestión de bases de datos

Entornos de desarrollo de gestión de bases de datos

Un entorno de desarrollo para la gestión de bases de datos es una herramienta de software que permite diseñar, administrar y consultar una base de datos mediante una interfaz gráfica, sin depender exclusivamente de la línea de comandos. Entre los más utilizados se encuentran phpMyAdmin y MySQL Workbench para MySQL, pgAdmin para PostgreSQL, o SQL Server Management Studio para SQL Server, cada uno adaptado al motor con el que trabaja. Estas herramientas suelen ofrecer funciones de diseño visual de tablas, ejecución y depuración de consultas, gestión de usuarios y permisos, y generación automática de diagramas entidad-relación a partir de un esquema existente. Elegir un entorno adecuado al motor y al nivel de experiencia del equipo facilita considerablemente las tareas cotidianas de administración y desarrollo de bases de datos.

Un estudiante utiliza MySQL Workbench para diseñar visualmente el diagrama entidad-relación de su proyecto antes de generar las tablas correspondientes.

Muchos de estos entornos de desarrollo permiten generar automáticamente el código SQL a partir de un diagrama diseñado gráficamente, invirtiendo el proceso habitual de diseño.
