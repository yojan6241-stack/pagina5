Análisis y diseño de aplicaciones

G1.01El ciclo de vida de un proyecto

El ciclo de vida de un proyecto

El ciclo de vida de un proyecto informático organiza el trabajo en fases sucesivas —análisis, diseño, implementación, pruebas y mantenimiento— que permiten controlar el alcance, los tiempos y los recursos desde la idea inicial hasta la puesta en producción. Cada fase produce entregables verificables que sirven de entrada a la siguiente, reduciendo el riesgo de construir algo que no responde a lo que realmente se necesitaba. Elegir un modelo de ciclo de vida adecuado (en cascada, iterativo o ágil) condiciona cómo se gestionan los cambios de requisitos durante el desarrollo.

Un equipo que desarrolla un sistema de matrícula universitaria documenta primero los requisitos, luego diseña el modelo de datos y finalmente programa e implanta el sistema en producción.

El modelo en cascada, uno de los primeros formalizados, exige cerrar por completo una fase antes de iniciar la siguiente, algo que los métodos ágiles flexibilizaron décadas después.

G1.02Conceptos de análisis de aplicaciones

Conceptos de análisis de aplicaciones

El análisis de aplicaciones consiste en estudiar el problema que la futura aplicación debe resolver, identificando los procesos de negocio, los datos que intervienen y las reglas que los gobiernan, sin entrar todavía en decisiones técnicas de implementación. Su resultado principal es una especificación de requisitos clara, que sirve de contrato entre quien encarga el sistema y quien lo construye. Un análisis incompleto suele traducirse en retrabajo costoso en fases posteriores del proyecto.

Antes de programar una tienda en línea, el analista entrevista al cliente para determinar cómo se gestionan el inventario, los pedidos y las devoluciones.

Numerosos estudios de ingeniería del software sitúan el costo de corregir un error de análisis, ya en producción, muchas veces por encima del costo de corregirlo durante esa misma fase.

G1.03Conceptos de diseño de aplicaciones

Conceptos de diseño de aplicaciones

El diseño de aplicaciones traduce los requisitos obtenidos en el análisis en una arquitectura concreta: qué módulos tendrá el sistema, cómo se comunican entre sí y qué estructura de datos sustentará su funcionamiento. A diferencia del análisis, que se centra en el «qué», el diseño responde al «cómo», estableciendo decisiones técnicas como el lenguaje, el motor de base de datos o el patrón arquitectónico a emplear. Un buen diseño facilita el mantenimiento y la escalabilidad futura del sistema.

Al diseñar un sistema de reservas hoteleras, el equipo decide separar la lógica de negocio de la capa de acceso a datos para poder cambiar de motor de base de datos sin reescribir toda la aplicación.

El patrón de diseño en capas, muy usado en aplicaciones empresariales, se popularizó precisamente para aislar los cambios en la base de datos del resto del sistema.

G1.04Conceptos generales del control de calidad

Conceptos generales del control de calidad

El control de calidad en el desarrollo de software abarca el conjunto de actividades planificadas para verificar que un producto cumple los requisitos especificados y está libre de defectos antes de llegar al usuario final. Incluye tanto revisiones estáticas de documentos y código como pruebas dinámicas sobre el sistema en ejecución, y se aplica de forma continua a lo largo de todo el ciclo de vida, no solo al final del proyecto. Su objetivo último es reducir el costo de los errores detectándolos lo antes posible.

Un equipo revisa el diseño de la base de datos antes de programarla, detectando así una clave ajena mal definida sin necesidad de esperar a las pruebas del sistema completo.

Detectar un defecto durante la fase de diseño suele costar, según estudios clásicos de ingeniería del software, una fracción muy pequeña de lo que cuesta corregirlo tras la puesta en producción.

G2.01Control de calidad de las especificaciones funcionales

Control de calidad de las especificaciones funcionales

Las especificaciones funcionales describen con precisión qué debe hacer el sistema desde el punto de vista del usuario, y su control de calidad verifica que sean completas, coherentes y verificables antes de iniciar el diseño técnico. Una especificación ambigua o contradictoria se traduce inevitablemente en errores de interpretación durante la programación. Técnicas como la revisión por pares o el uso de casos de uso ayudan a detectar huecos en la especificación antes de que cuesten tiempo de desarrollo.

Al revisar la especificación de un sistema de facturación, el equipo detecta que no se indica qué ocurre si un cliente no tiene dirección fiscal registrada, y lo aclara antes de programar.

Las revisiones formales de especificaciones, introducidas por IBM en los años setenta bajo el nombre de inspecciones de Fagan, siguen siendo una referencia en control de calidad de software.

G2.02Seguimiento de los requisitos de usuario

Seguimiento de los requisitos de usuario

El seguimiento de requisitos consiste en mantener trazabilidad entre cada requisito de usuario y los elementos del sistema que lo satisfacen —módulos de diseño, código, casos de prueba—, de modo que sea posible verificar en cualquier momento que todo lo solicitado se ha implementado y probado. Esta disciplina resulta especialmente valiosa cuando los requisitos cambian durante el proyecto, ya que permite medir el impacto de cada cambio. Sin trazabilidad, es fácil perder de vista requisitos secundarios a medida que el proyecto crece.

Un equipo mantiene una matriz de trazabilidad donde cada requisito queda vinculado a su módulo de código y a su caso de prueba correspondiente.

La gestión formal de requisitos como disciplina propia se consolidó especialmente en los años noventa, con la aparición de herramientas dedicadas de trazabilidad.

G2.03Introducción a las bases de datos

Introducción a las bases de datos

Una base de datos es un conjunto organizado de datos relacionados entre sí, almacenados de forma estructurada para facilitar su acceso, gestión y actualización, y se administra mediante un sistema gestor de bases de datos (SGBD) que controla el almacenamiento físico, la seguridad, la concurrencia y la recuperación ante fallos. A diferencia de un simple archivo de datos, una base de datos está pensada para ser compartida por múltiples usuarios y aplicaciones sin perder consistencia. Su diseño adecuado es la base sobre la que se construye cualquier sistema de información moderno.

Una empresa centraliza en una única base de datos la información de clientes, pedidos y productos, en lugar de mantenerla dispersa en hojas de cálculo independientes.

El término «base de datos» comenzó a popularizarse en los años sesenta, en paralelo al desarrollo de los primeros sistemas gestores comerciales.

G2.04Evolución histórica de las bases de datos

Evolución histórica de las bases de datos

Las bases de datos han evolucionado desde los sistemas de archivos planos de los años sesenta, pasando por los modelos jerárquico y de red, hasta la aparición del modelo relacional propuesto por Edgar Codd en 1970. Este modelo se impuso comercialmente en las décadas de los ochenta y noventa gracias a su solidez matemática y a la estandarización del lenguaje SQL, y más recientemente han surgido los sistemas NoSQL y NewSQL orientados a grandes volúmenes y datos poco estructurados. Esta evolución responde a necesidades cambiantes de escalabilidad y flexibilidad.

Un sistema bancario de los años setenta basado en un modelo jerárquico migra décadas después a un motor relacional para ganar flexibilidad en sus consultas.

Edgar F. Codd publicó su artículo seminal sobre el modelo relacional, «A Relational Model of Data for Large Shared Data Banks», en 1970 mientras trabajaba en IBM.

G3.01Ventajas e inconvenientes de las bases de datos

Ventajas e inconvenientes de las bases de datos

Frente al almacenamiento en archivos independientes, las bases de datos ofrecen ventajas como la reducción de la redundancia, el mantenimiento de la integridad de los datos y el acceso concurrente controlado. Como contrapartida, exigen mayor complejidad de instalación y administración, un costo asociado al software gestor y al personal especializado, y una planificación cuidadosa de la seguridad y de las copias de respaldo. Evaluar estas ventajas e inconvenientes en cada proyecto evita adoptar una solución sobredimensionada o insuficiente.

Una pequeña tienda que antes registraba ventas en hojas de cálculo adopta una base de datos al notar inconsistencias entre los archivos usados por distintos empleados.

Los primeros sistemas gestores comerciales de los años setenta requerían equipos especializados de administradores dedicados exclusivamente a su operación.

G3.02Fundamentos del modelo relacional

Fundamentos del modelo relacional

El modelo relacional organiza los datos en tablas bidimensionales, llamadas relaciones, compuestas por filas (tuplas) y columnas (atributos), apoyándose en la teoría matemática de conjuntos y en la lógica de predicados. Su fortaleza radica en representar tanto los datos como las asociaciones entre ellos con la misma estructura tabular, sin punteros físicos explícitos. Sobre este modelo se definen operaciones formales de álgebra relacional que sustentan lenguajes de consulta como SQL.

Una tabla de «Clientes» con columnas para nombre, dirección y correo electrónico ejemplifica una relación del modelo relacional, donde cada fila es un cliente distinto.

El álgebra relacional, base teórica del modelo, fue formalizada por Codd apoyándose en conceptos tomados directamente de la teoría de conjuntos matemática.

G3.03Estructura del modelo relacional

Estructura del modelo relacional

La estructura del modelo relacional se compone de relaciones (tablas), atributos (columnas) y tuplas (filas), organizadas de forma que cada tabla representa un conjunto homogéneo de entidades. Cada atributo toma valores de un dominio definido, y el orden de filas y columnas no tiene significado formal dentro del modelo. Esta estructura tabular permite representar relaciones complejas mediante claves que vinculan unas tablas con otras.

Una tabla «Empleados» y una tabla «Departamentos» se vinculan mediante una columna común que representa la estructura relacional entre ambas entidades.

A diferencia del modelo jerárquico que lo precedió, el modelo relacional no exige rutas de acceso predefinidas para llegar a un dato.

G3.04El concepto de relación

El concepto de relación

En el modelo relacional, una relación es matemáticamente un subconjunto del producto cartesiano de los dominios de sus atributos, aunque en la práctica se visualiza simplemente como una tabla con nombre. Cada relación debe tener un nombre único dentro del esquema y un conjunto fijo de atributos, cada uno con su propio dominio de valores válidos. Este concepto formal es lo que permite aplicar operaciones de álgebra relacional de manera consistente sobre cualquier base de datos.

La relación «Productos» define atributos como código, nombre y precio, y cada fila concreta de la tabla es una tupla que pertenece a esa relación.

El término «relación» proviene directamente de la teoría matemática de conjuntos, y es distinto —aunque a menudo se confunde— del concepto coloquial de «relación» entre tablas.

GRUPO4

Claves y restricciones

G4.01Propiedades de las relaciones

Propiedades de las relaciones

Las relaciones del modelo relacional cumplen propiedades formales: no existen tuplas duplicadas, el orden de las filas y columnas es irrelevante, y cada celda contiene un único valor atómico, sin grupos repetitivos. Estas propiedades garantizan que cualquier motor relacional pueda operar sobre las tablas de forma predecible, sin depender del orden físico de almacenamiento. Violar la atomicidad, por ejemplo guardando varios valores en una sola celda, suele ser síntoma de un diseño que necesita normalizarse.

Una tabla «Pedidos» que intentara guardar varios productos separados por comas en una sola columna estaría violando la propiedad de atomicidad de los valores.

La ausencia de tuplas duplicadas en una relación pura es lo que, en la práctica, obliga a definir siempre una clave primaria en cada tabla.

G4.02Atributos y dominio de los atributos

Atributos y dominio de los atributos

Un atributo es cada una de las columnas que componen una relación, y su dominio es el conjunto de valores válidos que puede tomar, definido por un tipo de dato y, opcionalmente, por restricciones adicionales. Definir dominios precisos —por ejemplo, que un campo «edad» solo acepte enteros positivos— es una de las primeras líneas de defensa contra datos incoherentes en la base de datos. El SGBD rechaza automáticamente cualquier valor que no pertenezca al dominio declarado.

El atributo «género» de una tabla «Libros» puede definirse con un dominio limitado a los valores «ficción», «ensayo» o «poesía», rechazando cualquier otro texto.

Aunque SQL estándar no ofrece un tipo «dominio» universal en todos los motores, muchos gestores permiten simularlo mediante restricciones CHECK sobre la columna.

G4.03Claves: candidatas, primarias, alternativas, ajenas

Claves: candidatas, primarias, alternativas, ajenas

Una clave candidata es cualquier conjunto mínimo de atributos que identifica de forma única cada tupla de una relación; de entre todas las candidatas se elige una como clave primaria, y las restantes se consideran claves alternativas. Una clave ajena, por su parte, es un atributo o conjunto de atributos que referencia la clave primaria de otra tabla, materializando así las relaciones entre entidades. Este sistema de claves es lo que permite reconstruir asociaciones complejas a partir de tablas simples.

En una tabla «Empleados», el DNI y el número de empleado pueden ser ambos claves candidatas; si se elige el número de empleado como primaria, el DNI queda como clave alternativa.

El término «clave ajena» (foreign key) fue acuñado precisamente para describir cómo una tabla «toma prestada» la identidad de otra para expresar una relación.

G4.04Restricciones de integridad: entidades, referencial

Restricciones de integridad: entidades, referencial

La integridad de entidad exige que ninguna columna que forme parte de la clave primaria admita valores nulos, garantizando que toda fila sea identificable de forma única. La integridad referencial, por su parte, exige que todo valor de una clave ajena exista realmente como clave primaria en la tabla referenciada, o sea nulo si el diseño lo permite. Juntas, estas restricciones evitan referencias «huérfanas» y datos inconsistentes entre tablas relacionadas.

Si la tabla «Pedidos» tiene una clave ajena que apunta a «Clientes», la integridad referencial impide insertar un pedido cuyo cliente no exista en la tabla «Clientes».

Muchos motores relacionales permiten configurar acciones automáticas —como CASCADE— para mantener la integridad referencial cuando se elimina una fila referenciada.

GRUPO5

Modelo entidad-relación

G5.01El modelo entidad-relación

El modelo entidad-relación

El modelo entidad-relación, propuesto por Peter Chen en 1976, es una herramienta conceptual para representar gráficamente los datos de un dominio antes de traducirlos a tablas relacionales, centrándose en las entidades del mundo real y en cómo se relacionan entre sí. Su principal ventaja es que resulta comprensible tanto para analistas técnicos como para usuarios de negocio, sirviendo de puente entre el análisis y el diseño físico de la base de datos. A partir de un diagrama entidad-relación bien construido, el paso a tablas relacionales resulta prácticamente mecánico.

Antes de crear las tablas de un sistema universitario, el analista dibuja un diagrama con las entidades «Alumno», «Curso» y «Matrícula» y las relaciones entre ellas.

Peter Chen presentó el modelo entidad-relación en un artículo de 1976 que sigue citándose como referencia obligada en el diseño conceptual de bases de datos.

G5.02Entidades, relaciones y atributos

Entidades, relaciones y atributos

En el modelo entidad-relación, una entidad representa un objeto o concepto del mundo real sobre el que se desea almacenar información (por ejemplo, un cliente o un producto), una relación describe cómo se asocian dos o más entidades entre sí, y un atributo es una propiedad que describe a una entidad o a una relación. Distinguir correctamente estos tres elementos es el primer paso para construir un diagrama entidad-relación coherente. Un error común de quienes empiezan es confundir una relación con una entidad débil.

En un sistema de biblioteca, «Libro» y «Socio» son entidades, «Préstamo» es la relación entre ellas, y «fecha de devolución» es un atributo de esa relación.

Algunas entidades, llamadas «débiles», no pueden existir sin depender de otra entidad, como una línea de pedido que no tiene sentido sin el pedido al que pertenece.

G5.03Diagramas entidad-relación

Diagramas entidad-relación

Un diagrama entidad-relación (DER) representa gráficamente las entidades, sus atributos y las relaciones entre ellas usando una notación estandarizada de rectángulos, óvalos y rombos, o notaciones más modernas como el pie de gallo (crow's foot). Estos diagramas documentan de forma visual las cardinalidades —uno a uno, uno a muchos, muchos a muchos— que después determinarán cómo se implementan las claves ajenas en el modelo físico. Un buen DER facilita enormemente la comunicación con el cliente antes de comprometer decisiones técnicas.

Un DER muestra que un «Cliente» puede realizar muchos «Pedidos», pero cada «Pedido» pertenece a un único «Cliente», es decir, una relación uno a muchos.

La notación de pie de gallo, muy usada hoy en herramientas de diseño, resulta más compacta que la notación original de Chen para representar cardinalidades.

G5.04Teoría de normalización

Teoría de normalización

La teoría de normalización, desarrollada también por Codd, estudia cómo descomponer relaciones que presentan redundancias o anomalías en relaciones más pequeñas y mejor estructuradas, sin perder información. Se apoya en el concepto de dependencia funcional, que describe cómo el valor de unos atributos determina el valor de otros dentro de una tabla. Esta teoría proporciona el marco formal sobre el que se definen las distintas formas normales.

Una tabla que mezcla datos de empleados y de los departamentos a los que pertenecen, repitiendo el nombre del departamento en cada fila, es candidata a normalizarse.

Codd introdujo la primera, segunda y tercera formas normales en artículos publicados entre 1970 y 1971, sentando las bases de toda la teoría posterior.

GRUPO6

Normalización I

G6.01El proceso de normalización

El proceso de normalización

El proceso de normalización aplica de forma sucesiva un conjunto de reglas —las formas normales— a las relaciones de un esquema, con el objetivo de eliminar redundancias y evitar anomalías de inserción, actualización y borrado. Cada forma normal exige el cumplimiento de la anterior, por lo que el proceso avanza de manera incremental hasta alcanzar el nivel de normalización requerido por el proyecto. En la práctica, la mayoría de los sistemas de gestión se normalizan hasta la tercera forma normal.

Un diseñador detecta que, en una tabla no normalizada, actualizar la dirección de un cliente obliga a modificar decenas de filas repetidas, y decide normalizar el esquema.

Aunque existen hasta cinco o seis formas normales formalmente definidas, en el diseño de aplicaciones comerciales rara vez se aplica más allá de la tercera.

G6.02Tipos de dependencias funcionales

Tipos de dependencias funcionales

Una dependencia funcional describe una relación entre atributos de una tabla en la que el valor de un atributo (o conjunto de atributos) determina de forma unívoca el valor de otro. Se distinguen dependencias funcionales completas, cuando dependen de toda la clave, y parciales, cuando dependen solo de una parte de una clave compuesta; también existen las dependencias transitivas, en las que un atributo depende de otro que a su vez depende de la clave. Identificar correctamente estas dependencias es el paso previo indispensable a cualquier normalización.

En una tabla con clave compuesta (código de curso, código de alumno), el nombre del curso depende solo del código de curso, lo que constituye una dependencia parcial.

Las dependencias funcionales, formalizadas matemáticamente por Codd, permiten demostrar de manera rigurosa por qué una tabla determinada no está bien estructurada.

G6.03Primera forma normal (1FN)

Primera forma normal (1FN)

Una relación está en primera forma normal cuando todos sus atributos contienen valores atómicos, es decir, indivisibles, y no existen grupos de columnas repetitivas para representar valores múltiples. Cumplir la 1FN es el requisito mínimo para que una tabla se considere parte del modelo relacional puro. Una tabla que almacena varios teléfonos de un mismo cliente en una sola columna, separados por comas, no cumple esta condición.

Una tabla «Clientes» con una columna «teléfonos» que contiene «555-1234, 555-5678» se descompone en una tabla aparte «Teléfonos» para cumplir la primera forma normal.

La 1FN es, de las cinco formas normales clásicas, la única que se considera parte de la propia definición del modelo relacional y no una optimización adicional.

G6.04Segunda forma normal (2FN)

Segunda forma normal (2FN)

Una relación está en segunda forma normal cuando, además de cumplir la primera forma normal, todos los atributos que no forman parte de la clave dependen completamente de la clave primaria, y no solo de una parte de ella. Esta forma normal solo tiene sentido cuando la tabla posee una clave primaria compuesta por varios atributos. Eliminar dependencias parciales evita que se repita información innecesariamente cada vez que cambia un componente de la clave.

En una tabla con clave (código de curso, código de alumno) donde el nombre del curso solo depende del código de curso, esa columna se traslada a una tabla «Cursos» aparte para alcanzar la 2FN.

La segunda forma normal, tal como la definió Codd, resulta irrelevante en tablas cuya clave primaria consta de un único atributo, ya que no puede haber dependencias parciales.

GRUPO7

Normalización II y lenguajes

G7.01Tercera forma normal (3FN)

Tercera forma normal (3FN)

Una relación está en tercera forma normal cuando, cumpliendo la segunda forma normal, ninguno de sus atributos no clave depende transitivamente de la clave primaria, es decir, no depende de otro atributo que a su vez depende de la clave. Alcanzar la 3FN es el nivel de normalización más habitual en el diseño de bases de datos comerciales, por ofrecer un buen equilibrio entre integridad y rendimiento. Eliminar dependencias transitivas evita anomalías de actualización cuando cambia un dato intermedio.

En una tabla «Empleados» donde el código de departamento determina el nombre del departamento, ese nombre se traslada a una tabla «Departamentos» separada para cumplir la 3FN.

Muchos sistemas de producción se detienen deliberadamente en la tercera forma normal, considerando que ir más allá aporta poca ganancia práctica frente a la complejidad añadida.

G7.02Otras formas normales (4FN, 5FN)

Otras formas normales (4FN, 5FN)

Más allá de la tercera forma normal existen la forma normal de Boyce-Codd, la cuarta forma normal, que elimina dependencias multivaluadas, y la quinta forma normal, que trata dependencias de unión más complejas. Estas formas normales avanzadas se aplican en escenarios muy específicos donde persisten redundancias no capturadas por la 3FN, y su uso es mucho menos frecuente en el diseño de aplicaciones cotidianas. Aplicarlas exige un análisis detallado de las dependencias entre atributos.

Una tabla que relaciona profesores con los idiomas que hablan y los cursos que pueden impartir, de forma independiente entre sí, puede requerir descomponerse según la cuarta forma normal.

La forma normal de Boyce-Codd, más estricta que la 3FN, fue propuesta por Raymond Boyce y Edgar Codd como una corrección a ciertos casos que la tercera forma normal no cubría.

G7.04Tipos de lenguajes de bases de datos relacionales

Un administrador usa sentencias DDL para crear una tabla, DML para insertar registros en ella y DCL para conceder permisos de lectura a otro usuario.

G8.01El lenguaje de definición de datos (DDL)

El lenguaje de definición de datos (DDL)

El lenguaje de definición de datos (DDL) agrupa las instrucciones SQL que crean y modifican la estructura de una base de datos: CREATE, ALTER y DROP, aplicadas sobre tablas, índices, vistas u otros objetos del esquema. A diferencia del DML, que opera sobre los datos contenidos en las tablas, el DDL opera sobre la propia estructura que los contiene. En la mayoría de los motores, las instrucciones DDL se ejecutan de forma implícita y no pueden deshacerse con un simple ROLLBACK.

Un administrador ejecuta una instrucción CREATE TABLE para definir la estructura de una nueva tabla «Clientes» con sus columnas y tipos de datos.

En muchos sistemas gestores, cada instrucción DDL provoca automáticamente un COMMIT implícito de cualquier transacción en curso, algo que sorprende a quien lo desconoce.

Tipos de datos del lenguaje

G9.01El lenguaje de manipulación de datos (DML)

El lenguaje de manipulación de datos (DML)

El lenguaje de manipulación de datos (DML) agrupa las instrucciones SQL que operan directamente sobre los datos almacenados en las tablas: SELECT para consultar, INSERT para insertar, UPDATE para modificar y DELETE para eliminar. A diferencia del DDL, las instrucciones DML sí pueden deshacerse mediante ROLLBACK dentro de una transacción, lo que las hace más seguras para operaciones cotidianas. El correcto uso del DML es la base del trabajo diario con cualquier base de datos relacional.

Una aplicación de ventas ejecuta una instrucción INSERT cada vez que se registra un nuevo pedido, y una instrucción SELECT cada vez que se consulta el historial de un cliente.

A diferencia del DDL, casi todas las instrucciones DML pueden agruparse en una única transacción y deshacerse por completo si algo falla a mitad de proceso.

G9.02Construcción de consultas de selección

Construcción de consultas de selección

Es, con diferencia, la instrucción SQL más utilizada en el día a día, ya que la mayoría de las operaciones de un sistema de información consisten en consultar datos existentes. Dominar el SELECT es el punto de partida obligado para cualquier trabajo con bases de datos.

La instrucción SELECT nombre, precio FROM Productos WHERE precio > 100 recupera únicamente los productos cuyo precio supera cien unidades.

Construcción de consultas de modificación

Omitir la condición WHERE provoca que la modificación se aplique a todas las filas de la tabla, un error frecuente y potencialmente muy costoso en entornos de producción. G10.01Construcción de consultas de borrado

Construcción de consultas de borrado

Las consultas de borrado, construidas con la instrucción DELETE, eliminan filas de una tabla según una condición especificada en la cláusula WHERE, sin afectar la estructura de la tabla en sí. G10.02Cláusulas de agrupación y ordenación

Cláusulas de agrupación y ordenación

La cláusula GROUP BY agrupa las filas de una consulta según el valor de una o varias columnas, permitiendo aplicar funciones agregadas a cada grupo por separado, mientras que ORDER BY ordena el resultado final según los criterios indicados, de forma ascendente o descendente. G11.01Tratamiento de valores nulos

Tratamiento de valores nulos

Un valor nulo en SQL representa la ausencia de dato o un valor desconocido, y se comporta de forma especial en comparaciones y cálculos: cualquier operación aritmética o lógica con un nulo produce, por lo general, otro nulo, por lo que no puede compararse con «=» sino con los operadores especiales IS NULL e IS NOT NULL. Ignorar este comportamiento es una fuente frecuente de errores sutiles en consultas y en filtros de aplicaciones. Diseñar bien qué columnas admiten nulos es parte del diseño de integridad de la tabla.

La condición WHERE telefono IS NULL identifica correctamente a los clientes sin teléfono registrado, mientras que WHERE telefono = NULL nunca devuelve resultados.

En la lógica de tres valores de SQL —verdadero, falso e indeterminado— cualquier comparación que involucre un nulo se evalúa como indeterminada, no como falsa.

G11.02Construcción de consultas combinadas

Construcción de consultas combinadas

G11.03Unión, intersección y diferencia de consultas

Unión, intersección y diferencia de consultas

SQL ofrece operadores de conjuntos —UNION, INTERSECT y EXCEPT (o MINUS, según el motor)— que combinan los resultados de dos o más consultas SELECT compatibles en su número y tipo de columnas. UNION reúne todas las filas de ambas consultas eliminando duplicados (o UNION ALL, conservándolos), INTERSECT devuelve solo las filas presentes en ambas, y EXCEPT devuelve las filas de la primera consulta que no aparecen en la segunda. Estos operadores resultan útiles cuando los datos que se desean combinar provienen de fuentes o tablas distintas.

La consulta SELECT ciudad FROM Clientes UNION SELECT ciudad FROM Proveedores devuelve la lista combinada, sin repeticiones, de todas las ciudades presentes en ambas tablas.

Entornos de desarrollo de gestión de bases de datos

Un entorno de desarrollo para la gestión de bases de datos es una herramienta de software que permite diseñar, administrar y consultar una base de datos mediante una interfaz gráfica, sin depender exclusivamente de la línea de comandos. Entre los más utilizados se encuentran phpMyAdmin y MySQL Workbench para MySQL, pgAdmin para PostgreSQL, o SQL Server Management Studio para SQL Server, cada uno adaptado al motor con el que trabaja. Elegir un entorno adecuado al motor y al nivel de experiencia del equipo facilita considerablemente las tareas cotidianas de administración y desarrollo.

Un estudiante utiliza MySQL Workbench para diseñar visualmente el diagrama entidad-relación de su proyecto antes de generar las tablas correspondientes.

Muchos de estos entornos permiten generar automáticamente el código SQL a partir de un diagrama diseñado gráficamente, invirtiendo el proceso habitual de diseño.
